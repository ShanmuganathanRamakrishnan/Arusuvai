# Round 4 addendum — uncertainty and self-review were both understated

Moved out of `CLAUDE.md` on 2026-08-12. Read this when you are touching
uncertainty derivation, the unverified-energy denominator, or anything that
records a review status.

These were places where the code *followed* the rules in `CLAUDE.md` and still
produced the failure those rules exist to prevent. That is a stricter bug than
rounds 1–3: it means "the doc's rule is implemented" is not sufficient evidence
the rule works — the test has to perturb an input and check the output actually
moves, not just check the rule is mentioned.

**Status was added on the move (2026-08-12), and it changes how this file
reads.** In `CLAUDE.md` all five items were written as imperatives — "Add
`Ingredient.composition_uncertainty`", "Make the field mandatory per macro",
"Test this directly" — as though none were built. All five are built. Carried
across unchanged, this file would have presented finished work as an outstanding
queue, which is the failure the restructure rule exists to catch. Each item
below keeps its original argument and gains a dated status line. One rule
generated by this round is **not** here: it lives in `CLAUDE.md`'s standing
mistakes list, because it is a blind-spot warning and cannot be fetched on
demand.

---

## 1. Composition uncertainty is a separate axis from process uncertainty

**Status: BUILT.** `Ingredient.composition_uncertainty` exists
(`core/foods/models.py`), driven by `Ingredient.verified`, with registered
defaults. `core/foods/nutrition_of.py` combines it with process uncertainty for
the displayed interval.

`Recipe.process_uncertainty` (oil uptake, cooking loss) is not the only source
of error — the underlying ingredient composition data itself carries
uncertainty, and at the time this was written that was silently treated as zero.
A verified-against-IFCT ingredient gets a tight registered default; an
unverified fixture-sourced one gets a wide registered default (itself an
`Evidence`-backed constant, not a bare literal). The displayed interval must
combine composition uncertainty, weighted by each ingredient's share of that
macro, with process uncertainty.

A dish that is 96% rice/lentil/vegetable and 4% griddle oil must not display a
tighter band than the rice/lentil/vegetable data actually supports. A narrow
band on mostly-unverified composition data is the same false-precision failure
this project exists to prevent in the LLM, committed instead by the data layer
— and it is worse than a bare unqualified number, because it actively asserts
the error is small.

## 2. Missing uncertainty must never default to most-confident

**Status: BUILT for composition; the successor gap is finding 41, still OPEN.**
Composition uncertainty is mandatory per macro and never zero —
`composition_uncertainty_for` refuses rather than returning 0.0. D10 closed the
recipe-level case (finding 2): a recipe with no `process:` line must now declare
either `preparation: uncooked` or the macros it cannot quantify. **Finding 41 is
the same defect one level down and is not fixed** — a recipe that does carry a
constant still derives 0.0 for every macro it does not touch. D12 re-scoped it
by measurement: 65.2% of the library's protein arrives on served-basis rows
whose zero is earned; the real gap is the other 34.8%.

If a macro's uncertainty is unset, it must not read as `0.0`. Make the field
mandatory per macro (fail the load on omission) or require an explicit
`unassessed` sentinel that maps to a wide registered default. The cheapest
authoring path must never produce the most confident-looking output.

## 3. No nutritional number may be hand-duplicated outside `citations.py`

**Status: BUILT.** Process uncertainty is derived at load time, not pasted.
`d4b_mutations.py` row R2 grades the mutate-a-constant test.

This includes a derived uncertainty figure pasted into a recipe YAML file. A
recipe's stored `process_uncertainty` value must be computed at load time from
the current constant in `citations.py` plus the recipe's declared exposure (e.g.
oil grams as a fraction of dish weight) — never hand-computed once and pasted
in. If a constant changes, every recipe depending on it must change too,
automatically, on next load.

Test this directly: mutate a constant and assert dependent recipes' computed
uncertainty changes. A test that only checks a fixed YAML value against itself
cannot catch this class of bug.

## 4. The unverified-energy threshold needs the correct denominator, both ways

**Status: BUILT.** D6 closed finding 20. `nutrition_of._unverified_energy`
attributes per ingredient line, charging a line once whether its composition
record or its process constant is unverified — union, not sum. Measured on all
four passing plates the answer is **100.0%**, not the 37–59% the old rule
reported. See `docs/methodology.md`, "The unverified-energy fraction, measured
correctly".

A recipe is not "X% unverified" because some process constant on it is
unverified — it is unverified in the proportion of its energy that constant
actually contributes, not the whole dish. Conversely, unverified *ingredient
composition* must also count toward the total: a recipe with a fully verified
process but unverified composition data is not thereby "verified."

## 5. A self-edited mechanism-match review dict is not a structural fix

**Status: BUILT.** `Grade.PROJECT_ESTIMATE` exists in
`core/nutrition/citations.py` and is rejected at registration when combined with
`verified=True`.

`verified=True` must only ever be set by a human who opened the primary source.
The same standard applies to any "mechanism confirmed" review status.
Self-attestation by the constant's own author can only ever record "no matching
source found" or "not yet reviewed" — never a positive "match confirmed."

A genuine confirmed-match state requires a second party's sign-off, tracked
separately from who registered the constant, or a dedicated evidence grade
(`PROJECT_ESTIMATE`: self-reviewed, single-author) that is categorically
ineligible to satisfy the mechanism-match requirement or count toward
"reviewed" in the shipping threshold, no matter what its own checklist says.

## 6. State plainly whether anything can ship as validated today

**Status: BUILT and the answer is no.** `docs/methodology.md`, "Nothing can
currently ship as validated (2026-07-21)". `dev_mode` is a distinct designation
from `validated` and is permanently on.

If every registered `Evidence` is currently `verified=False`, the honest
conclusion — once the denominator above is fixed — may be that nothing can
presently ship as validated. Say so directly in `docs/methodology.md`, dated.
That is a defensible thing for a portfolio project to state. Discovering it
silently after `core/planner` is built on the assumption that some plans clear
the threshold is not.

Keep a `dev_mode` designation distinct from `validated`, so plan generation and
testing can proceed on admittedly-unverified data, loudly labeled, without
conflating "the pipeline runs" with "the pipeline can stand behind a number."
